Chapter 2

How it’s built — every choice and its rejected twin

A handful of Python files, two runtime dependencies (numpy, Pillow), no GPU, no compile step. The interesting parts are not the lines — they’re the forks in the road.

The architecture in one picture

Choice 1 — Two phases instead of one

Chosen: classify, then replay

Run the batch once to learn who escapes; then re-run only escapees, plotting as you go. Costs extra arithmetic: every escaping orbit is iterated twice.

Why: it keeps every inner operation a whole-array numpy expression. Vectorization demands uniform control flow — you cannot have per-point “start recording now” branches without falling out of SIMD-friendly array ops.

Rejected: single pass with orbit buffers

Record every orbit into per-sample arrays while iterating, then scatter once. Looks cheaper on paper; in practice the recording gathers into Python-level lists or object arrays, memory balloons to GB, and the scatter dominates. There is a middle path — fixed per-sample ring buffers of 64 slots in a (N, 64) array — viable, but the code triples in complexity for a modest win on CPU.

Choice 2 — bincount instead of np.add.at

Turning point-coordinates into histogram hits is a scatter-add. The obvious tool is np.add.at(hist, idx, 1), which was notoriously slow before NumPy 1.25 added a fast path for ufunc.at when the operands are aligned and need no casting (NumPy 1.25.0 release notes). The renderer uses np.bincount(flat_indices, minlength=W*H) instead: one vectorized call that does not rely on that fast path, so the choice does not depend on the NumPy version. The cost is allocating a fresh 4M-entry array per call, so the plotter buffers indices and flushes at 24M points per bincount, amortizing the allocation.

Choice 3 — compaction cadence

Points escape at wildly different times; after 30 steps a 3M-sample batch is mostly dead weight. Every k steps the survivors are compacted — boolean-masked down to the living — so work per step decays like the survival curve. k is a compromise: too small and the masking overhead (a full copy of six arrays) dominates; too large and you keep iterating corpses. k = 32 for quadratics, k = 8 for the transcendental mutations (they can overflow float64 in a handful of steps past their escape radii — which brings us to the bug).

The bug the renders exposed

Symptom: quadratic-family renders (powers, ship, tricorn, celtic, buffalo, julia) came out visibly sparse and ate mysterious amounts of phase-1 time.

Cause: a diverging point grows geometrically: past radius 2 a quadratic orbit takes ~11 more steps to overflow float64 into inf, and one step later inf − inf yields NaN. NaN fails every comparison — nan > 4 is False — so from that moment the escape test can never fire again: the point is misclassified as a prisoner forever, and it keeps riding along in the arrays burning cycles until the iteration cap. With compaction every 32 steps, a large share of the escaping orbits was silently dropped from those maps (how large depends on the check interval and the iteration cap).

Fix: one guard — (r > 4) | ~np.isfinite(r) — treat NaN as escaped. The original single-map renderer had it; the generalized farm rewrite dropped it. The regression test now compares the vectorized classifier against a per-step scalar reference on five maps.

Moral: NaN is not a crash; it is a very quiet wrong answer. Floating-point escape tests need explicit infinite/NaN handling, and reference-test your fast path against a dumb one.

Choice 4 — analytic culling of the interior

Points inside the main cardioid or the period-2 bulb can never escape (a conjugacy argument pins their orbits to bounded disks), and both regions have closed-form membership tests. Culling them before iteration removes about 11.9% of the uniform draws in the classic and Nebulabrot window (the two regions have area 3π/8 + π/16 = 7π/16 ≈ 1.374, out of 3.4 × 3.4), and it is sound because culled points contributed nothing to an escape-only histogram anyway. (The Antibuddhabrot must not cull: prisoners are its entire subject.)

Choice 5 — float64 and honest precision

float32 would double throughput on paper. Rejected: squaring amplifies rounding, deep orbits would visibly kink, and — decisive — the overflow-to-NaN hazard arrives sooner. The cos(x²) mutations already oscillate punishingly at |x| > 10; halving mantissa there produces visibly different pictures. The escape radii for transcendental maps (|y|, |x|, or |z| at 100–1000) are heuristic bailouts, except the y-cosine map’s |x| > 100 test, which is a proven bound (see the math chapter); orbits that overflow between checks are caught by the NaN guard.

The bincount scatter and the compaction copies are memory-bound random traffic rather than arithmetic, which is the kind of work a GPU handles well.

Alternative architectures

ArchitectureWhy not (or when)
C + OpenMP, same two-phase design Nothing wrong with it — it’s just a weekend of memory-management for a result numpy already produces in minutes. The natural next step if renders move to 8K.
CUDA / OpenCL, atomic adds into VRAM histogram The real endgame: scatter-add is what GPUs are for. Cost: a CUDA toolchain, and the two-phase trick becomes optional (thread-per-sample with early-exit is fine on GPU).
WebGL/WebGPU in-browser Chosen for the playground’s mini-renderer in spirit (canvas, JS): instant sharing, zero install. Plain JS is fast enough to watch the photograph develop live.
Single-pass orbit bufferingComplexity for break-even; rejected (Choice 1).
float32 everywhereVisible artifacts on deep orbits; rejected (Choice 5).
Multiprocessing inside one job Used in practice as four sharded CLI processes.

Quality control by numbers

python brot_farm.py qc prints four statistics (the center of mass as x and y) for every finished farm render: mean luminance, visible fraction (the share of pixels brighter than 0.05), a top/bottom correlation about the image midline, and the center of mass. The correlation is a mirror test only when the plot window is centred on the real axis (it is not for the tan and sinh mutations). A lopsided center of mass on a symmetric map points to a bug; on an asymmetric map it means the mutation worked. Because histograms are cached, an image whose numbers look off can be re-toned without re-running the sampling — measure, re-tone, measure.

What would make it better

Smarter sampling

Uniform sampling is simple and unbiased, but in a zoomed view most shots land on orbits that never cross the frame. Boundary-weighted importance sampling and Metropolis-style seed mutation are known options for zoomed views (brot_samplers.py has experimental versions of both).

GPU backend

A CUDA kernel (one block per sample batch, atomicAdd into a texture) would turn “minutes” into “seconds”, unlock 8K and animation. The two-phase structure dissolves: classify and plot in the same pass.

Animation pipeline

The cached-histogram design already supports keyframed tone-maps; a zoom/rotation film needs only re-windowed histograms — resample the same orbit data through a different affine window.

Proper imaging pipeline

HDR EXR output, filmic tone-mapping (ACES-ish) instead of gamma-only, per-channel p95 anchors for chroma balance, and optional wavelet denoise to smooth Monte-Carlo grain without losing filigree.
